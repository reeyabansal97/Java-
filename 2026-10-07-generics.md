# Java Day 11: Generics

## What problem do they solve?

Before Java 5, collections held plain `Object`s:

```java
List list = new ArrayList();
list.add("hello");
list.add(42);                        // nothing stops this
String s = (String) list.get(1);     // ClassCastException at RUNTIME
```

Two problems:
1. You had to **cast** everything you took out.
2. Type mistakes only showed up **at runtime**, often far from where the wrong item was added.

**Generics** let you tell the compiler what type a collection (or class, or method) works with:

```java
List<String> list = new ArrayList<>();
list.add("hello");
list.add(42);              // compile error, caught immediately
String s = list.get(0);    // no cast needed
```

Moving errors from runtime to compile time is the whole point.

## Generic classes

You can write your own. `T` is a **type parameter**, a placeholder filled in when the class is used:

```java
public class Box<T> {
    private T value;

    public void set(T value) { this.value = value; }
    public T get() { return value; }
}

Box<String> nameBox = new Box<>();
nameBox.set("Reeya");
String name = nameBox.get();

Box<Integer> numBox = new Box<>();
numBox.set(5);
```

One class, type-safe for any type. The `<>` on the right is the **diamond operator**: the compiler infers the type from the left side.

Naming convention: `T` (type), `E` (element, used by collections), `K`/`V` (key/value, used by maps). So `Map<K, V>` reads as "a map from keys of type K to values of type V."

## Generic methods

A method can declare its own type parameter, written before the return type:

```java
public static <T> T firstOrDefault(List<T> list, T fallback) {
    return list.isEmpty() ? fallback : list.get(0);
}

String s = firstOrDefault(List.of("a", "b"), "none");
Integer n = firstOrDefault(List.of(), 0);
```

The compiler figures out `T` from the arguments.

## Bounded types: restricting `T`

Sometimes `T` must have certain abilities. To find a maximum, the elements must be comparable (Java Day 9):

```java
public static <T extends Comparable<T>> T max(List<T> list) {
    T best = list.get(0);
    for (T item : list) {
        if (item.compareTo(best) > 0) best = item;
    }
    return best;
}
```

`T extends Comparable<T>` means "T can be any type, as long as it implements `Comparable<T>`." Without the bound, `compareTo` wouldn't compile, because the compiler wouldn't know `T` has that method.

Note: in generics, `extends` covers **both** classes and interfaces.

## A surprising rule: `List<Integer>` is not a `List<Number>`

`Integer` is a subclass of `Number`. But:

```java
List<Integer> ints = new ArrayList<>();
List<Number> nums = ints;   // compile error
```

Why? If it were allowed:

```java
nums.add(3.14);   // a Double is a Number, so this would be legal...
Integer i = ints.get(0);   // ...but ints now contains a Double: crash
```

Both variables point to the **same list** (Java Day 2), so allowing this would break type safety. This property is called **invariance**.

## Wildcards: flexibility where it's safe

To write a method that accepts a list of *any* numeric type, use a **wildcard**:

```java
public static double sum(List<? extends Number> numbers) {
    double total = 0;
    for (Number n : numbers) total += n.doubleValue();
    return total;
}

sum(List.of(1, 2, 3));        // List<Integer> ✓
sum(List.of(1.5, 2.5));       // List<Double>  ✓
```

- **`? extends T`**: "some unknown subtype of T." You can safely **read** items as `T`, but you **can't add** to it, because the compiler doesn't know the exact type.
- **`? super T`**: "some unknown supertype of T." You can safely **add** `T`s, but reading gives you only `Object`.

Mnemonic: **PECS, "Producer Extends, Consumer Super."** If the parameter *gives you* items (you read from it), use `extends`. If it *takes* items (you write into it), use `super`.

You've already used this without noticing: `Collections.sort` and `Comparator` methods use these wildcards in their signatures.

## Type erasure: generics are a compile-time feature

Here's the catch. After compiling, the JVM **doesn't know** about generic types. `List<String>` and `List<Integer>` both become plain `List` in the bytecode (Java Day 1). The compiler checks types and inserts the casts for you, then **erases** the type information.

This was done so new generic code could run alongside old pre-Java-5 code. It has visible consequences:

```java
new T();                        // not allowed: the type isn't known at runtime
T[] arr = new T[10];            // not allowed, for the same reason
if (list instanceof List<String>) {}   // not allowed: the runtime only sees List
List<int> nums;                 // not allowed: generics work only with reference types
```

That last one is why you write `List<Integer>`, not `List<int>`, which brings in autoboxing (Java Day 2).

## Raw types: don't use them

`List list = new ArrayList();` (no type) is a **raw type**. It turns off all generic checking and exists only for backward compatibility. The compiler warns about it. Always specify the type.

## Common pitfalls

- **Using raw types.** You lose all the safety generics provide.
- **Expecting `List<Integer>` to be accepted as `List<Number>`.** Use `List<? extends Number>` instead.
- **Trying to add to a `List<? extends T>`.** The compiler forbids it.
- **Trying `new T()` or `new T[]`.** Type erasure makes these impossible.
- **Writing `List<int>`.** Generics need reference types; use the wrapper `Integer`.

## Interviewer follow-ups

**"What is type erasure?"** Generic type information exists only at compile time. The compiler checks types and inserts casts, then removes the type parameters, so at runtime `List<String>` is just `List`. It was done for backward compatibility with pre-generics code.

**"Why can't you assign `List<Integer>` to `List<Number>`?"** Both would point to the same list, so code holding the `List<Number>` could add a `Double`, corrupting the list of integers. Generics are invariant to prevent this. Use `List<? extends Number>` when you only need to read.
